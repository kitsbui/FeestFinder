# FeestFinder: notes for coding agents

EDM event discovery for Vietnam and Asia (HCMC, Hà Nội, Đà Nẵng, Nha Trang, Bangkok, Tokyo, Singapore, Bali): club nights, raves and festivals of electronic music only. Vietnamese first, bilingual everywhere. Live at https://feestfinder.com. The brand is spelled FeestFinder; code names, packages and folders keep `festfinder`.

## Where things are

| Path | What it is |
| --- | --- |
| `festfinder-backend/` | The API and the production server: Node 24, TypeScript run directly (no build step), Fastify, Postgres on Supabase. feestfinder.com reaches it through the Next proxy. |
| `festfinder-backend/src/routes/` | One file per area. `admin/*` serves the team, `organizer/*` the organisers' back office, `frontend.ts` serves the `/ui` files with their caching and redirects the old `/ops` addresses, `seo.ts` serves robots, the sitemap, llms.txt and OG images. |
| `festfinder-backend/src/services/` | Logic shared by routes: `seo.ts` (one builder for every page's SEO/AIO), `oauth.ts`, `notify.ts`, `messaging.ts`, `tickets.ts`, `resale.ts`… |
| `festfinder-backend/src/services/ingest/` | Event intelligence: `adapters/` (website JSON-LD, ICS, Ticketmaster), `normalize.ts`, `resolve.ts` (deterministic dedupe), `confidence.ts` (rules + freshness), `run.ts` (the pipeline), `fetch.ts` (robots.txt, per-host spacing). Imports never publish: they merge into an event or wait in the review queue. |
| `festfinder-backend/src/lib/` | `i18n.ts` (`L(en, vi)`, genres), `places.ts` (countries and cities with timezone, currency, bounds; synced to the tables after every migration), `styles.ts` (music styles, event types, classifier), `money.ts`, `errors.ts`, `validate.ts` (`parse`, `limit`, `csv`), `time.ts` (`atZone`, `dateIn`, `isoIn` for event times; the `vn*` helpers for back-office dates), `format.ts`. |

| `festfinder-backend/test/` | `node --test` on PGlite in memory. `helpers.ts` has `setup()`, `people.ts` has `emailUser()`, and `fixtures/seed.ts` is the demo data. Demo data exists only in the tests. |
| `festfinder-backend/e2e/` | Playwright. `next/` holds the checks of the site, the Console, Studio and the artist studio; `playwright.next.config.ts` runs them against a production Next build with the API behind it. |
| `festfinder-frontend/ui/` | The files the site loads from `/ui`: `map/ff-map.js` (the map, loaded by `FF.loadMap()` in `festfinder-web/src/runtime/ff.ts`), `assets/` (brand images, favicons) and `vendor/` (MapLibre + pmtiles). | `docs/` | `CURRENT_ARCHITECTURE.md`, `TECH_DEBT.md`, `FEESTFINDER_IMPLEMENTATION_PLAN.md` (the event-intelligence plan and the decisions behind it), `FEESTFINDER_ROADMAP.md`, `DESIGN_GOVERNANCE.md` (the design gates of every pull request, the five-person test of every major phase, the numbers read every two weeks) and `RELIABILITY.md` (the service levels, the outside uptime check `.github/workflows/uptime.yml`, what to do when one is missed, the incident log: each incident a line and a test). ## Commands

Run from `festfinder-backend/` unless noted.

```bash
npm run typecheck          # tsc for src+test and for e2e; noUnusedLocals/Parameters are on
npm test                   # every API test (a few minutes)
node --test test/auth.test.ts                  # one file
npm run test:screens       # Playwright: e2e/next against a production Next build (3100) and its own API (4100, own PGlite)
npm run dev                # the API on :4000 against the staging database in .env
```

For the Next front, run `npm run dev` / `npm run build` from `festfinder-web/`. Both copy `public/ui/` first. `npm run lint` there runs type-aware ESLint: no errors, and no more warnings than the budget in its `package.json` (lower it when you fix some). In `festfinder-backend/`, `npm run lint` runs oxlint type-aware (through typescript-go, so it reads TypeScript 7), configured in `.oxlintrc.json`: no errors, and no more warnings than its `--max-warnings` budget (lower it when you fix some); `npm run lint:warnings` lists them.

## Rules this codebase follows

- **Copy:** server text uses `L('English', 'Tiếng Việt')`. Screen text on the site is `{en, vi}` pairs in `festfinder-web/src/kd/copy/` and each screen's `copy.ts`, read with `pick()` (one line: `tx()`; never `pair[lang]`). The web defaults to Vietnamese. The public pages also speak Thai, Japanese and Indonesian (design v2 phase 10, `?lang=th|ja|id`, each rewritten to a page of its own like `?lang=en`, in `next.config.ts`): their lines are `copy/asia/{th,ja,id}.ts`, keyed by the English line and sent only with a page in that language (`InLang` in `kd/ui/in-lang.tsx`, which every public page wraps itself in); a line they lack, the back offices and the API's text (`dataLang`: the API writes Vietnamese and English) read English. A new public line gets its three translations there: `npm run lint` runs `scripts/check-copy.ts` (design v2 phase 15), which refuses a `{en, vi}` pair in the public files it lists (`PUBLIC`) without a line in every language (`SAME` names the lines kept as they are); `/kit` shows every public line in the five languages with "Tải CSV" for a native speaker, `npm run copy:export` writes the same CSV, `npm run copy:import <csv>` reads the corrections back. `e2e/next/layout.spec.ts` walks the public pages in each language at 390, 1280 and 1440px, and the target and axe checks walk them in English too. A live listing's description in one language only gets the other from Claude (`services/translate.ts`, the `translateDescriptions` job, `ANTHROPIC_API_KEY`): `events.auto_translated` (migration 048) names the machine-written languages, the page shows "Bản dịch tự động" and the original under "Bản gốc", and a language someone wrote is never overwritten. Dates and numbers go through `kd/format.ts` and `INTL[lang]`, never a hard-coded locale.
- **Lean UI:** the user wants titles and actions, not explanations. Add a hint only for a format rule. No tips cards, no "why we ask" lines. No status line that counts the results or says when a list was updated.
- **Look:** the site (Kính đêm v2, design phase 0 on 2026-10-17): `surface-0` `#08090a`. Colour tokens are named for their role in `festfinder-web/src/kd/theme.css`, the only file that writes a hex colour: `surface-0/1/2`, `line-1/2`, `fg-1/2/3`, `inverse` / `on-inverse`, `info`, `lime`, `on-accent`, `ok` / `warn` / `bad`, `map`. Colour says one sentence: turquoise `info` `#00D9D0` is information (style names, links, the chosen tab, row or pin, counts, "free"); the turquoise → lime gradient (`--gradient-accent`: `#00D9D0` · `#72E679` · `#E4F222`) is the one action a screen exists for (`buttonClass({ tone: 'acc' })`, with `glow` on the one that leads the page), the "featured" tag (`kd-tag-featured`) and the logo's flags; lime alone is the focus ring and the glow; status is a dot with a word. Four button tones (`acc`, `default` outlined, `ghost`, `danger`); radii 4 / 8 / 16 and the pill; glass only over a photo or a map. `npm run lint` in `festfinder-web` runs `scripts/check-tokens.ts`: no hex colour outside `theme.css` (a literal that must stay says `tokens-ok`), no old token name (`scripts/tokens-v2.ts` renames them, `npm run tokens:rename`), and no more arbitrary `[Npx]` values than its budget, which only goes down. One type family, Noto Sans, for words and numbers alike (self-hosted from `@fontsource-variable/*`, declared in `kd/fonts.css`, which `festfinder-web/scripts/fonts-css.ts` writes on `npm run copy-ui`: a Vietnamese page fetches only the latin and vietnamese files; Thai text the Thai file; Noto Sans JP's stylesheet goes to `public/fonts/` and `kd/ui/script-fonts.tsx` adds it only on a page with CJK text; no Google Fonts request, and the CSP allows none; no monospace face: numbers line up with `kd-num`), icons from `@phosphor-icons/react` (Regular, imported per icon). Pages are full width on desktop: `.kd-wrap` has no max width, only the gutter (`--kd-gutter`: 16, 32, then up to 64px); long text keeps `max-w-read`, and card grids add columns rather than widen. The app's screens (`/app/…`: tickets, checkout, notifications, settings, alerts, the group plan, the guide, live mode, recap) wear the site's frame (`kd/app/root.tsx`, design v2 phase 4): its nav on top and, on a phone, its tab bar, which a screen's dock sits on; buying from the list never changes frame. A back button in the app or the Studio wizard goes back where the person came from on this site (`BackLink` / `goBack` in `kd/ui/back-link.tsx`), its fixed page only when they arrived from elsewhere. The site's frame (design v2 phase 1, `kd/web/chrome.tsx`): on a computer one bar with the logo, four places (Sự kiện, Nghệ sĩ, Dự án, Nhà tổ chức), the search field (⌘K or Ctrl+K; an icon from 900 to 1200px), VI · EN, "Đăng sự kiện" and the account menu; on a phone the logo on top ("Đăng sự kiện" is in "Tôi" and the footer there, owner 2026-10-18: the top is the newcomer's) and a tab bar at the bottom of every public page (Sự kiện, Bản đồ, Đã lưu, Tôi; `TabBar` with `edge`; four since design v2 phase 12, owner 2026-10-18), and the search an icon at the top that opens the "Tìm" sheet with the other places and the styles (Nghệ sĩ and Dự án are in "Tôi" too). Signed out, a heart saves on the device (`ff:saves`, `deviceSaves` in `kd/runtime.tsx`, owner 2026-10-18): `/saved` shows those nights, and signing in moves them to the account. The workspaces (attending, the craft, the Console for the team) are one list too (`kd/ui/workspaces.tsx`), in the account menu, the hub and the switcher at the head of every back office's rail; admins reach the Console there (`isTeam` in `kd/craft.ts`), not from the bar. Every screen fits the width of the device and nothing scrolls sideways, anywhere (the owner's rule): no `min-w-[…]` wrapper, no `overflow-x-auto` box; a row of tabs (`.kd-tabs`) or chips (`.kd-hscroll`) wraps to a second line. `e2e/next/layout.spec.ts` checks every role's screens at 390, 768 and 1440px, and `e2e/next/wcag.spec.ts` runs axe on the same screens at 390 and 1440px (no serious or critical WCAG 2.1 AA violation): an accessible name starts with the visible words, tabs that are links are a `nav` and tabs that switch in place a `tablist` with arrow keys (`Tabs` in `kd/ui/shell.tsx`), a sheet gives focus back to what opened it, and every page starts with a skip link to its `<main>` (`kd/ui/skip-link.tsx`, in the root layout). Every screen in `e2e/next/perf.spec.ts` loads on a throttled phone without its layout jumping (CLS 0.05 at most), with its largest content painted within 2.5 s (2.0 s on the home and event pages; design v2 phase 14) and within the JS budget it lists, which only goes down: a box that arrives after the first paint holds its final size, a page that loads its content holds the screen's height before its footer (`min-h-dvh`), no margin on a page's first box, choices made in the render rather than in an effect after it, and what few people open (the sign-in sheet, the role picker, the search sheet, the feedback sheet, the app's first run; on the event page the share and report sheets, the stage timetable, resale, Hỏi đáp, Hype, the photo wall and the ambassadors, design v2 phase 14) loads when it opens or after the page (`next/dynamic`). `visual.spec.ts` also shoots two regions on their own (the event hero, the home page's filter bar), where a whole page's 1 % would miss a change. No browser scrollbar takes room: `kd.css` hides them all and `kd/ui/scrollbars.tsx` (in the root layout) draws a 3px thumb over whatever scrolls, only while it scrolls; don't style scrollbars per screen.

- **The runtime:** there is one, `festfinder-web/src/runtime/ff.ts` (`FF`, with `src/kd/runtime.tsx`). The map stays in `festfinder-frontend/ui/map/ff-map.js`, which the Next build copies and `FF.loadMap()` loads.
- **Validation:** validate input with zod through `parse()`. Throw `AppError` helpers so the error reaches the client as `{error: {code, message}}`. Build SQL only with positional parameters (`$1` or `SqlParams.p()`). Interpolate column names only from fixed lists. A NUL character anywhere in a request (address, query, body) is refused as `invalid_input` before any handler (`app.ts`); Postgres would fail on it.
- **Sign-in:** Google first; a one-time code by SMS, Zalo, WhatsApp or email; a password. Phone codes go out through real providers when configured (phase 17, owner 2026-10-19: `services/sms.ts`, Twilio or eSMS.vn for SMS with `SMS_PROVIDER`, Zalo ZNS with `ZALO_OA_*` and a rotating refresh token kept in `provider_tokens`, migration 047), else through the operator's messaging webhook; a provider's "never" answer is a `PermanentDeliveryError`, the rest retries with backoff; the code is never logged. `/me/connections/sms|zalo|wa/start` proves a phone the same way (SMS links no app). OAuth comes back through `/auth/oauth/:provider/return`, which redirects with `?auth=…&via=…` or `?auth_error=…`. `GET /auth/providers` says which ways in are configured (`sms`, `zalo` and `wa` are on with a provider, the webhook, or a preview's dev codes), and the sign-in card shows only those, phone ways first. `GET /auth/session?optional=1` answers `{user: null}` instead of a 401.
- **Personas and admin:** every account attends (a fan); besides that it has at most one craft, artist or organiser (`user_roles`, migration 033: the API refuses a second with `one_craft`, `POST /me/roles/switch` swaps them and keeps both profiles; the screens switch from the account menu and the workspace rails, `kd/craft.ts`). Listed profiles are claimed, never duplicated. Admin comes only from the `ADMIN_EMAIL` allowlist on a Google sign-in with a verified email: never add a route, role choice or shared password that grants it, and never write the allowlist into the repo. An organiser's listing needs a 16:9 cover before it can be sent (`missingForSubmit`, design v2 phase 8; the team may publish without one, as a Radar find often has none, and the Console's numbers show the share of coming listings with a real cover). Every listing someone sends in (Studio, the community form, a change to a live listing) waits in the Console's review queue and every admin is told in the app, by push and by email (`askForReview`, `notifyAdmins`); what an admin posts goes live at once (`teamSession`). A change to a live listing keeps it on sale while it waits (`needs_review_*`, migration 040): approving clears the flag, rejecting puts the old values back.
- **Projects:** anyone signed in (no craft needed) pitches an idea for a night at `/p` (`routes/projects.ts`, `services/projects.ts`, migration 034): what it is, its budget, what it looks for (investment, sponsors, artists, a venue, a partner) and sponsor packages. The team reviews it before it is public (`/console/projects`); publishing needs a confirmed phone, like every post. Others offer (`invest`, `sponsor`, `perform` from an active artist profile, `venue`, `partner`); an accepted offer shows both sides each other's contact. FeestFinder never takes, holds or moves money, and every project page says so; never add a payment to it. A project linked to its event puts the accepted sponsors on the event page and in its JSON-LD (`Event.sponsor`).
- **Artists and gigs:** follower counts never rank an artist, a directory or a gig applicant. Network lines are read from events with their evidence, not stored. An artist's gig report is a source, never a publisher. The artist directory lives at `/a` (`/a/style/<style>`, `/a/city/<city>`) because `/artists` is the API. It lists only profiles an artist runs (made or claimed) or the team verified (`artistKind` 'owned', `services/artists.ts`; the owner confirmed on 2026-10-17 that a verified profile counts as owned); the team hides a profile the site should not show from `/console/artists` ("Ẩn khỏi site", `artists.hidden_at`, migration 046: out of the directory, search, the sitemap, suggestions and the lineups' links, its page 404, nothing deleted, shown again with the same switch); every other name events show, from a lineup or Radar, waits at `/a/radar` (`?kind=unclaimed`) with "Đây là tôi". The directory says which with tabs and their counts (Có hồ sơ · Từ Radar · Nhận booking: `/a`, `/a/radar`, `/a?booking=1`), never with a line explaining it; its cards are square (the photo, else the initials large: `Art` layout `mono`) with the next show, two to a row on a phone. An artist's page has no banner repeating the name: their cover only when they have one, then tabs (Sắp diễn · Mix · Đã diễn · Giới thiệu; `EventTabs` opens `#<key>` and `?mix=`), the latest mix beside them. "Đây là tôi" and "Tôi là nghệ sĩ" send `role_picker_shown` (role, surface), so claims can be counted. A follow is of a profile (`artist_follows.artist_id`, migration 041), never of an unclaimed name ("Nhắc khi có show" adds it to Smart Alerts instead), and nobody follows their own page; when an artist takes a profile over, follows and alerts of the name move to it. A profile an artist runs is the official one for its name, and lineups meet it by handshake (`services/lineup.ts`, `event_artists.confirmed_*`): an organiser who lists the artist asks them in the app to confirm ("Đây là tôi" / "Không phải tôi", a dispute unlinks the name for that event), an artist's gig report on a listed night asks the organiser to add them, and the profile shows only confirmed shows. Followers and following are read from real follows only (`services/follows.ts`, migration 042): people follow artist profiles, organisers and people (`user_follows`, `PUT /me/follows/people/:id`); a profile's following is what the accounts that run it follow; nobody follows their own page or themselves; `organizers.followers_count` is kept equal to its follows by a trigger and never seeded. A person manages both lists on their profile (`kd/ui/follows.tsx`).
- **Analytics:** `FF.track(name, props)` only with a name in `CLIENT_EVENTS` and keys in `ALLOWED_PROPS` (`services/analytics.ts`); never an email, a name or an IP. Nothing leaves without `POSTHOG_KEY`. Every page reports LCP, INP and CLS as `web_vital` {kind, value, rating} (`kd/ui/vitals.tsx`, in the root layout), and the browser's uncaught errors go to `POST /client-errors` (`routes/client-errors.ts`: the API's own reporter, Sentry with `SENTRY_DSN`; paths without their query, three per page at most; `kd/feedback/telemetry.ts`).
- **Production data:** there is no demo data and no seed in production, and there must never be a fallback database. Production and staging Supabase projects refuse each other's labels.
- **Places, time and money:** never hard-code a city, a UTC offset or `₫`. A city comes from `lib/places.ts` (add one there; it is synced to the `cities` table); an event's instants use its city's timezone (`atZone`, `isoIn`); prices are whole units of `events.currency`, shown with `formatMoney` / `money()` (`festfinder-web/src/kd/format.ts`). A sold night with no price (`entry_mode` paid, `price_from` 0, what Radar finds on a page that gives none) is `priceUnknown`, never free: "Chưa rõ giá", and its ticket button goes through `/go` to the page it was found on (design v2 phase 11). Radar never reads an age: its default "All ages" is not shown. FeestFinder checkout and ticket tiers are VND only. FeestFinder charges buyers no fee, on tickets or on resale: what a buyer pays is the price less any discount.
- **EDM only:** the one genre is `EDM` (`lib/i18n.ts` `GENRES`, a database check since migration 031); people filter by its styles (`lib/styles.ts` `STYLES`, `?style=`). An import that names another genre and no EDM style is dropped (`OTHER_GENRES`), one with no style waits for review, and approving it makes it EDM. Sources that list every kind of music set `requireStyle`.
- **Posted or Radar:** every event and artist is one or the other, and the site says which. `events.origin` is `radar` when nobody on FeestFinder posted it (no `organizer`, `community`, `team` or `artist` source), only Feest Radar (ingestion) found it; `refreshConfidence` keeps it current, so an organiser claiming it makes it posted. An artist is Radar when nobody runs or verified the profile and every event it plays is Radar (`ORIGIN` in `services/artists.ts`). `?origin=posted|radar` filters `/events`, `/events/map` and `/artists`; `facets.origin` / `origins` count them. On the site, `kd/ui/origin.tsx`: `RadarTag` on anything Radar found (only its sign on a card, `compact`; the word on the event page), the "Nguồn" filter (Mọi nguồn · Đã đăng · Radar) on the home page's list (`/`), and the artist directory's tabs (Có hồ sơ · Từ Radar · Nhận booking), and a Radar event's page names Feest Radar instead of its placeholder organiser. The local preview seeds a few Radar finds (`SEED_RADAR=1`, `test/fixtures/radar.ts`); the screen tests do not.
- **Sources:** ingestion is one more source next to organisers and the community, never a publisher. No adapter for Resident Advisor or Facebook (their terms forbid it); their links are kept as provenance only. New adapters go in `services/ingest/adapters/` and `ADAPTERS`, with fixture tests in `test/ingest.test.ts` (no live requests).
- **Feest Radar:** two placeholder organisers hold events nobody runs yet (`services/community.ts` `PLACEHOLDER_ORGS`, `organizers.placeholder`, migration 044): Feest Radar (`/o/feest-radar`) holds what ingestion finds, Cộng đồng FeestFinder (`/o/cong-dong`) what people send in (the community form, an artist's gig report). Both are `is_community` (claimable, nobody to warn or tell), and each is made with its first event, never on an empty database. Styles follow Beatport's dance genres (`lib/styles.ts`, mirrored in `festfinder-web/src/kd/genre.ts`, a test checks both), and a lineup of known artists (`lib/known-artists.ts`, whole names only) gives a night its style when the source names none. Every candidate gets a fit score for the team (`services/ingest/fit.ts`: the project's criteria and its people's, with reasons; Console queue sorts and filters by it); a new find under `FIT_FLOOR` is dropped as `low_fit`, unless it is a festival Radar watches (`lib/festivals.ts`: `world` brands such as Tomorrowland, Ultra, EDC, Defqon.1 and Verknipt are kept in any known Asian city, launched or not, listed anywhere, highlighted on cards and on the home page, and first in the queue; `asia` brands only weigh in). A Radar find (origin radar) is marked `expired` a day after `ends_at`, the end of its last day (`services/ingest/expire.ts`, hourly job); nothing is deleted and an admin can restore it.
- **Images:** only an event's own media is uploaded (`POST /uploads?purpose=cover|logo|recap`: its cover and logo, and the photos fans take at it). Every other picture (a person's photo, an artist's photo and cover, an organiser's logo and cover, a project's cover, moments) is an https link checked by `probeImage` / `imageChange` (`services/remote-images.ts`) when it changes, and weekly by the `checkRemoteImages` job; the screens use `kd/ui/image-link.tsx`. Never add an upload purpose for a profile. Linked images load with `referrerPolicy="no-referrer"`, and a broken one leaves the initials or the art (`kd/ui/covers.tsx`). A picture's framing (the point to keep in view and a zoom) travels in its link as `#ff=x,y,z` (`lib/frame.ts`, `kd/frame.ts`): `Art`, `Avatar` and `FramedThumb` draw it, the editor is `FrameButton` (`kd/ui/frame-editor.tsx`, on every image field), the API checks, compares and notifies by the link without it (a new framing of the same picture is not checked again or sent to review), and SEO drops it.
- **Mixes:** an artist's SoundCloud, Mixcloud and Spotify sets (`lib/mixes.ts`, `routes/mixes.ts`). Never store or render a service's oEmbed HTML: `embedFrom` rebuilds the player's address on the hosts in `EMBED_HOSTS`, which must match `frame-src` in `festfinder-web/next.config.ts`. Nothing from a service loads before play. Likes and comments never rank anyone; commenting needs a confirmed phone.
- **Rides:** "Đặt xe" opens Grab, Be or Green SM by the country of the event's city (`lib/rides.ts`), never a hard-coded city. No app fills the destination until a partner link says how; the address is copied instead. The phone remembers the app chosen (`ff:ride-app`, browser only): the next tap opens it at once with "Đổi app" in the toast, and a city with one app opens it at once; an app with a universal link (Be's OneLink) opens through it on an iPhone (`web/event/ride.tsx`).
- **Event actions:** "Chỉ đường" opens Google Maps' route to the venue at once (`web/event/directions.ts`), never an anchor on the page. "Thêm lịch" opens the person's own Google Calendar with the night filled in (`authuser` is their email; Android opens the calendar app with an INSERT intent), and the `.ics` stays in its menu for Apple and Outlook (`web/event/calendar.tsx`).
- **Feedback:** the widget (`kd/feedback/`, in the root layout) sends `POST /feedback` (`routes/feedback.ts`); the server stamps the ticket and who sent it, and keeps the page's telemetry to its fixed list (paths without their query). Screenshots are served to the team only and deleted after 90 days; a GitHub issue never names who sent the report.
- **Advertising:** posting an event is free and goes through review. Promoting one is a request from Studio (`/studio/ads`, `routes/organizer/ads.ts`: the event, placements from `EVENT_AD_PLACEMENTS`, a budget, dates within the event, a note); brands book from `/advertise` with their details (`POST /ad-inquiries`: logo, website and social pages, product images as links, category from `AD_CATEGORIES`, contact, budget, dates, placements, cities). Every admin is told; the team answers both in `/console/featured` with a reply, and an approved request becomes an `ad_campaigns` row that only runs inside its dates. Ads are sold in VND (`lib/ads.ts`).
- **Ticket buttons:** every one goes through `/go/<event>` (`routes/outbound.ts`), never straight to `ticket_url`: it counts the click, picks FeestFinder's checkout or the seller, and adds a partner's tracking (`services/partners.ts`, `/console/partners`).
- **Map:** the map view asks `/events/map` when it opens and on "search this area" only, never on pan. The basemap is two self-hosted PMTiles archives, cut by `festfinder-backend/scripts/build-tiles.sh`: `MAP_OVERVIEW_URL` (the whole world, zoom 0–6, drawn below zoom 7) and `MAP_TILES_URL` (the listed cities, zoom 0–14, drawn from zoom 7, so no tile is drawn twice), on Vercel Blob (store `feestfinder-tiles`, `tiles/<planet build>/…`). Rebuild the tiles after adding a city, upload them under a new build folder and point the variables there.

## Caching (frontend.ts)

Outside development, the `/ui` URLs in CSS carry `?v=<content hash>`:
- `stampUrls()` adds it.
- Versioned files are `immutable`; the same file without it gets `max-age=3600`.
- Vercel starts a fresh CDN cache on every deployment.
- Responses for a signed-in person get `private, no-store` (`app.ts` onSend hook).
- Public reads without a session (`PUBLIC_READS` in `app.ts`) get `Vercel-CDN-Cache-Control: max-age=60, stale-while-revalidate=60` (only Vercel's CDN keeps them; the browser's `Cache-Control` stays `max-age=0, must-revalidate`, so it never shows a stale anonymous copy after sign-in) and vary on `X-FF-Session`, which the web proxy sets to 1 for a visitor with a session cookie and the web app's server renders (`lib/api.ts`) set to `render`; a request with it is never given or stored a shared copy. After a save, the screen calls `freshen` (`festfinder-web/src/kd/fresh.ts`, which posts to the route handler `app/kd-fresh/route.ts`; not a server function, which would refresh the router and drop filters kept in the address) so the public pages it changed render again at once. Never vary on `Cookie`: Vercel's CDN does not cache such a response.

## Deploying

- Two Vercel projects, both in `hnd1` (Tokyo), next to the Supabase database:
  - `feestfinder-web` (root directory `festfinder-web`) holds feestfinder.com (`www` and `feestfinder.vercel.app` redirect to it). Its proxy (`src/proxy.ts`) forwards every non-page path to the API with fetch, signed with `WEB_PROXY_SECRET` so the API sees each visitor (`festfinder-web/README.md`, "Deploy on Vercel").
  - `feestfinder` (root directory `festfinder-backend`) is the API, at `https://feestfinder-api.vercel.app` (the web project's `FF_API_ORIGIN`). Its `PUBLIC_BASE_URL` and `CORS_ORIGINS` stay `https://feestfinder.com`.
- Pushing to `main` deploys production on both projects (both are linked to GitHub with `main` as the production branch). The API's other branches get preview deployments on the staging database, and so do the web project's (`festfinder-web/vercel.json` builds every branch): a web preview reads the staging API through its Preview variables (`FF_API_ORIGIN` of the staging API and `FF_API_BYPASS`, the API's protection bypass secret: `festfinder-web/README.md`, Deploy on Vercel, step 6). Migrations run on boot.
- Work happens on a branch and reaches `main` by merge. CI (`.github/workflows/ci.yml`) runs on pushes to `main` and on pull requests.
- To ship the API from a branch without merging it, run `vercel deploy --prod --yes` from the repo root (the root `.vercelignore` leaves `festfinder-web` out).
- pg_cron calls `POST https://feestfinder.com/internal/jobs` every minute; the web proxy forwards it with its `Authorization`.
- There is no way back to the API's old screens: they were removed on 2026-10-09. To undo a bad web release, promote an earlier `feestfinder-web` deployment in Vercel (Instant Rollback).
- Secrets, such as `GOOGLE_CLIENT_SECRET`, are entered by the user in Vercel.

## Checking a change

1. `npm run typecheck`, then the test file for the area, then `npm test`; `npm run lint` in each package you changed.
2. Browser checks: `npm run test:screens` (the checks are in `e2e/next/`; CI runs them in three shards, `-- --shard=n/3`, each on its own build and database, so a file only relies on the files before it in its own third).
3. Add a test next to similar ones: API behaviour in `test/*.test.ts`, a page of the site or a back-office flow in `e2e/next/<area>.spec.ts`.
4. Design gates (`docs/DESIGN_GOVERNANCE.md`): a pull request that touches `festfinder-web` or `festfinder-frontend` ticks the "Thiết kế" checklist of `.github/pull_request_template.md` (`design-checklist.yml`); when its main screens differ from the base branch's (`visual.yml`, shot on the same runner), someone looks at the `visual-diff` artifact and adds the label `visual-ok`, which a new push takes off.
