# FeestFinder: notes for coding agents

EDM event discovery for Vietnam and Asia (HCMC, Hà Nội, Đà Nẵng, Nha Trang, Bangkok, Tokyo, Singapore, Bali): club nights, raves and festivals of electronic music only. Bilingual everywhere; Vietnamese addresses are the canonical ones, and a first visit reads English (owner, 2026-10-20). Live at https://feestfinder.com. The brand is spelled FeestFinder; code names, packages and folders keep `festfinder`.

## Where things are

| Path | What it is |
| --- | --- |
| `festfinder-backend/` | The API and the production server: Node 24, TypeScript run directly (no build step), Fastify, Postgres on Supabase. feestfinder.com reaches it through the Next proxy. |
| `festfinder-backend/src/routes/` | One file per area. `admin/*` serves the team, `organizer/*` the organisers' back office, `frontend.ts` serves the `/ui` files with their caching and redirects the old `/ops` addresses, `seo.ts` serves robots, the sitemap, llms.txt and OG images, `agent.ts` the read-only data for AI agents (`/list.md`, `/mcp`). |
| `festfinder-backend/src/services/` | Logic shared by routes: `seo.ts` (one builder for every page's SEO/AIO), `oauth.ts`, `notify.ts`, `messaging.ts`, `partners.ts` (the ticket sellers and their tracking), `attendance.ts` (who went to a night)… |
| `festfinder-backend/src/services/ingest/` | Event intelligence: `adapters/` (website JSON-LD, ICS, Ticketmaster), `normalize.ts`, `resolve.ts` (deterministic dedupe), `confidence.ts` (rules + freshness), `run.ts` (the pipeline), `fetch.ts` (robots.txt, per-host spacing). Imports never publish: they merge into an event or wait in the review queue. |
| `festfinder-backend/src/lib/` | `i18n.ts` (`L(en, vi)`, genres), `places.ts` (countries and cities with timezone, currency, bounds; synced to the tables after every migration), `styles.ts` (music styles, event types, classifier), `money.ts`, `errors.ts`, `validate.ts` (`parse`, `limit`, `csv`), `time.ts` (`atZone`, `dateIn`, `isoIn` for event times; the `vn*` helpers for back-office dates), `format.ts`. |
| `festfinder-backend/src/db/migrations/` | Numbered SQL files, applied on boot. The next one is `063_*.sql`. Never edit a migration that has shipped. |
| `festfinder-backend/test/` | `node --test` on PGlite in memory. `helpers.ts` has `setup()`, `people.ts` has `emailUser()`, and `fixtures/seed.ts` is the demo data. Demo data exists only in the tests. |
| `festfinder-backend/e2e/` | Playwright. `next/` holds the checks of the site, the Console, Studio and the artist studio; `playwright.next.config.ts` runs them against a production Next build with the API behind it. |
| `festfinder-frontend/ui/` | The files the site loads from `/ui`: `map/ff-map.js` (the map, loaded by `FF.loadMap()` in `festfinder-web/src/runtime/ff.ts`), `assets/` (brand images, favicons), `vendor/` (MapLibre + pmtiles) and `widget/ff-widget.js` (an organiser's calendar on their own site). Production runs this front at feestfinder.com; every path that is not one of its pages goes to the API through `src/proxy.ts`. |
| `docs/` | `CURRENT_ARCHITECTURE.md`, `TECH_DEBT.md`, `FEESTFINDER_IMPLEMENTATION_PLAN.md` (the event-intelligence plan and the decisions behind it), `FEESTFINDER_ROADMAP.md`, `DESIGN_GOVERNANCE.md` (the design gates of every pull request, the five-person test of every major phase, the numbers read every two weeks) and `RELIABILITY.md` (the service levels, the outside uptime check `.github/workflows/uptime.yml`, what to do when one is missed, the incident log: each incident a line and a test). ## Commands

Run from `festfinder-backend/` unless noted.

```bash
npm run typecheck          # tsc for src+test and for e2e; noUnusedLocals/Parameters are on
npm test                   # every API test (a few minutes)
node --test test/auth.test.ts                  # one file
npm run test:screens       # Playwright: e2e/next against a production Next build (3100) and its own API (4100, own PGlite)
npm run dev                # the API on :4000 against the staging database in .env
```

For the Next front, run `npm run dev` / `npm run build` from `festfinder-web/`. Both copy `public/ui/` first. `npm run lint` there runs type-aware ESLint: no errors, and no more warnings than the budget in its `package.json` (lower it when you fix some). In `festfinder-backend/`, `npm run lint` runs oxlint type-aware (through typescript-go, so it reads TypeScript 7), configured in `.oxlintrc.json`: no errors, and no more warnings than its `--max-warnings` budget (lower it when you fix some); `npm run lint:warnings` lists them.

## Rules this codebase follows

- **Copy:** server text uses `L('English', 'Tiếng Việt')`. Screen text on the site is `{en, vi}` pairs in `festfinder-web/src/kd/copy/` and each screen's `copy.ts`, read with `pick()` (one line: `tx()`; never `pair[lang]`). Each page's address names its language (`?lang=`, Vietnamese without it), but a person's first visit reads English and every visit after reads the last language they chose (owner, 2026-10-20): `src/proxy.ts` asks `langRedirect` (`kd/lang-pref.ts`) on every page request and moves a page to the language in the `ff_lang` cookie (English without one, `NEXT_PUBLIC_DEFAULT_LANG` overrides it: the screen checks build with `vi`), so someone who chose Vietnamese is never moved back to English, not even by a shared `?lang=en` link; crawlers, link previews and headless browsers are never moved. The language links say `?setlang=` (`chooseHref`): the proxy writes the cookie and opens the clean address, with or without JavaScript; `rememberLang` also keeps it in the device's storage (the back offices read it, `place.lang()`, English when none) and, signed in, in the account (`PATCH /me` `locale`). The switch in the bar is two flags (`ui/flags.tsx`, drawn by `theme.css`: Vietnam's for Vietnamese, the United States' for English, the page's own ringed in the information colour); Thai, Japanese and Indonesian are in the footer. The public pages also speak Thai, Japanese and Indonesian (design v2 phase 10, `?lang=th|ja|id`, each rewritten to a page of its own like `?lang=en`, in `next.config.ts`): their lines are `copy/asia/{th,ja,id}.ts`, keyed by the English line and sent only with a page in that language (`InLang` in `kd/ui/in-lang.tsx`, which every public page wraps itself in); a line they lack, the back offices and the API's text (`dataLang`: the API writes Vietnamese and English) read English. A new public line gets its three translations there: `npm run lint` runs `scripts/check-copy.ts` (design v2 phase 15), which refuses a `{en, vi}` pair in the public files it lists (`PUBLIC`) without a line in every language (`SAME` names the lines kept as they are); `/kit` shows every public line in the five languages with "Tải CSV" for a native speaker, `npm run copy:export` writes the same CSV, `npm run copy:import <csv>` reads the corrections back. `e2e/next/layout.spec.ts` walks the public pages in each language at 390, 1280 and 1440px, and the target and axe checks walk them in English too. A live listing's description in one language only gets the other from Claude (`services/translate.ts`, the `translateDescriptions` job, `ANTHROPIC_API_KEY`): `events.auto_translated` (migration 048) names the machine-written languages, the page shows "Bản dịch tự động" and the original under "Bản gốc", and a language someone wrote is never overwritten. Dates and numbers go through `kd/format.ts` and `INTL[lang]`, never a hard-coded locale.
- **Lean UI:** the user wants titles and actions, not explanations. Add a hint only for a format rule. No tips cards, no "why we ask" lines. No status line that counts the results or says when a list was updated.
- **Look:** the site (Kính đêm v2, design phase 0 on 2026-10-17): `surface-0` `#08090a`. Colour tokens are named for their role in `festfinder-web/src/kd/theme.css`, the only file that writes a hex colour: `surface-0/1/2`, `line-1/2`, `fg-1/2/3`, `inverse` / `on-inverse`, `info`, `lime`, `on-accent`, `ok` / `warn` / `bad`, `map`; the two flags of the language switch are drawn in `theme.css` too (`kd-flag-vn`, `kd-flag-us`), in their own colours, nowhere else. Colour says one sentence: turquoise `info` `#00D9D0` is information (style names, links, the chosen tab, row or pin, counts, "free"); the turquoise → lime gradient (`--gradient-accent`: `#00D9D0` · `#72E679` · `#E4F222`) is the one action a screen exists for (`buttonClass({ tone: 'acc' })`, with `glow` on the one that leads the page), the "featured" tag (`kd-tag-featured`) and the logo's flags; lime alone is the focus ring and the glow; status is a dot with a word. Four button tones (`acc`, `default` outlined, `ghost`, `danger`); radii 4 / 8 / 16 and the pill; glass only over a photo or a map. `npm run lint` in `festfinder-web` runs `scripts/check-tokens.ts`: no hex colour outside `theme.css` (a literal that must stay says `tokens-ok`), no old token name (`scripts/tokens-v2.ts` renames them, `npm run tokens:rename`), and no more arbitrary `[Npx]` values than its budget, which only goes down. One type family, Noto Sans, for words and numbers alike (self-hosted from `@fontsource-variable/*`, declared in `kd/fonts.css`, which `festfinder-web/scripts/fonts-css.ts` writes on `npm run copy-ui`: a Vietnamese page fetches only the latin and vietnamese files; Thai text the Thai file; Noto Sans JP's stylesheet goes to `public/fonts/` and `kd/ui/script-fonts.tsx` adds it only on a page with CJK text; no Google Fonts request, and the CSP allows none; no monospace face: numbers line up with `kd-num`), icons from `@phosphor-icons/react` (Regular, imported per icon). Pages are full width on desktop: `.kd-wrap` has no max width, only the gutter (`--kd-gutter`: 16, 32, then up to 64px); long text keeps `max-w-read`, and card grids add columns rather than widen. No public page has a side column (owner, 2026-10-20): one column, what sat beside it folded at its end; a profile (an artist's, the signed-in fan's) and the advertise form sit in a centred column (`max-w-page`, `--container-page` 1200px; the form `max-w-read`), a blog article in the middle at `max-w-read` (its editor `max-w-3xl`), and `Crumbs` `width` lines the trail up with it. - **The runtime:** there is one, `festfinder-web/src/runtime/ff.ts` (`FF`, with `src/kd/runtime.tsx`). The service worker's source is `festfinder-web/src/sw/sw.js`; `scripts/copy-ui.ts` writes `public/sw.js` (ignored by git) named after the build (`scripts/build-id.ts`: Vercel's commit, else the checkout's), so every deploy brings a new worker; every page registers it after load (`kd/ui/worker.tsx`, `runtime/pwa.ts`: `updateViaCache: 'none'`, a check when the page is seen and every 30 minutes) and an idle page reloads once when a new build takes over, never on a first visit. Installing (`kd/ui/install.tsx`): a strip on a phone from the second visit, right above the tab bar, once per device; "Cài ứng dụng" in "Tôi"; Chrome's own prompt or the steps for Safari and Chrome; "Phiên bản" in the settings. The browser checks block service workers except where a test allows them (`playwright.next.config.ts`). The map stays in `festfinder-frontend/ui/map/ff-map.js`, which the Next build copies and `FF.loadMap()` loads.
- **Validation:** validate input with zod through `parse()`. Throw `AppError` helpers so the error reaches the client as `{error: {code, message}}`. Build SQL only with positional parameters (`$1` or `SqlParams.p()`). Interpolate column names only from fixed lists. A NUL character anywhere in a request (address, query, body) is refused as `invalid_input` before any handler (`app.ts`); Postgres would fail on it.
- **Sign-in:** Google first; a one-time code by SMS, Zalo, WhatsApp or email (the email also carries a one-tap link, `GET /auth/email/:challenge/:code`; a proven email signs in or makes the account with no password step, phase 17); Facebook, Instagram and TikTok (`services/oauth.ts`, keys in Vercel); a password for those who set one. ## Caching (frontend.ts)

Outside development, the `/ui` URLs in CSS carry `?v=<content hash>`:
- `stampUrls()` adds it.
- Versioned files are `immutable`; the same file without it gets `max-age=3600`.
- Vercel starts a fresh CDN cache on every deployment.
- Responses for a signed-in person get `private, no-store` (`app.ts` onSend hook).
- Public reads without a session (`PUBLIC_READS` in `app.ts`) get `Vercel-CDN-Cache-Control: max-age=60, stale-while-revalidate=60` (only Vercel's CDN keeps them; the browser's `Cache-Control` stays `max-age=0, must-revalidate`, so it never shows a stale anonymous copy after sign-in) and vary on `X-FF-Session`, which the web proxy sets to 1 for a visitor with a session cookie and the web app's server renders (`lib/api.ts`) set to `render`; a request with it is never given or stored a shared copy. After a save, the screen calls `freshen` (`festfinder-web/src/kd/fresh.ts`, which posts to the route handler `app/kd-fresh/route.ts`; not a server function, which would refresh the router and drop filters kept in the address) so the public pages it changed render again at once. Never vary on `Cookie`: Vercel's CDN does not cache such a response.

  - `feestfinder-web` (root directory `festfinder-web`) holds feestfinder.com (`www` and `feestfinder.vercel.app` redirect to it). Its proxy (`src/proxy.ts`) forwards every non-page path to the API with fetch, signed with `WEB_PROXY_SECRET` so the API sees each visitor (`festfinder-web/README.md`, "Deploy on Vercel").
  - `feestfinder` (root directory `festfinder-backend`) is the API, at `https://feestfinder-api.vercel.app` (the web project's `FF_API_ORIGIN`). Its `PUBLIC_BASE_URL` and `CORS_ORIGINS` stay `https://feestfinder.com`.
- Pushing to `main` deploys production on both projects (both are linked to GitHub with `main` as the production branch). The API's other branches get preview deployments on the staging database, and so do the web project's (`festfinder-web/vercel.json` builds every branch): a web preview reads the staging API through its Preview variables (`FF_API_ORIGIN` of the staging API and `FF_API_BYPASS`, the API's protection bypass secret: `festfinder-web/README.md`, Deploy on Vercel, step 6). Migrations run on boot.
- Work happens on a branch and reaches `main` by merge. CI (`.github/workflows/ci.yml`) runs on pushes to `main` and on pull requests.
- To ship the API from a branch without merging it, run `vercel deploy --prod --yes` from the repo root (the root `.vercelignore` leaves `festfinder-web` out).
- pg_cron calls `POST https://feestfinder.com/internal/jobs` every minute; the web proxy forwards it with its `Authorization`.
- There is no way back to the API's old screens: they were removed on 2026-10-09. To undo a bad web release, promote an earlier `feestfinder-web` deployment in Vercel (Instant Rollback).
- Secrets, such as `GOOGLE_CLIENT_SECRET`, are entered by the user in Vercel.

## Checking a change

1. `npm run typecheck`, then the test file for the area, then `npm test`; `npm run lint` in each package you changed.
2. Browser checks: `npm run test:screens` (the checks are in `e2e/next/`; CI runs them in three shards, `-- --shard=n/3`, each on its own build and database, so a file only relies on the files before it in its own third).
3. Add a test next to similar ones: API behaviour in `test/*.test.ts`, a page of the site or a back-office flow in `e2e/next/<area>.spec.ts`.
4. Design gates (`docs/DESIGN_GOVERNANCE.md`): a pull request that touches `festfinder-web` or `festfinder-frontend` ticks the "Thiết kế" checklist of `.github/pull_request_template.md` (`design-checklist.yml`); when its main screens differ from the base branch's (`visual.yml`, shot on the same runner), someone looks at the `visual-diff` artifact and adds the label `visual-ok`, which a new push takes off.
