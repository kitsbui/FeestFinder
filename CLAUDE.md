# FeestFinder: notes for coding agents

EDM event discovery for Vietnam and Asia (HCMC, Hà Nội, Đà Nẵng, Nha Trang, Bangkok, Tokyo, Singapore, Bali): club nights, raves and festivals of electronic music only. Vietnamese first, bilingual everywhere. Live at https://feestfinder.com. The brand is spelled FeestFinder; code names, packages and folders keep `festfinder`.

## Where things are

| Path | What it is |
| --- | --- |
| `festfinder-backend/` | The API and the production server: Node 24, TypeScript run directly (no build step), Fastify, Postgres on Supabase. feestfinder.com reaches it through the Next proxy. |
| `festfinder-backend/src/routes/` | One file per area. `admin/*` serves the team, `organizer/*` the organisers' back office, `frontend.ts` serves the `/ui` files with their caching and redirects the old `/ops` addresses, `seo.ts` serves robots, the sitemap, llms.txt and OG images. |
| `festfinder-backend/src/services/` | Logic shared by routes: `seo.ts` (one builder for every page's SEO/AIO), `oauth.ts`, `notify.ts`, `messaging.ts`, `tickets.ts`, `resale.ts`… |
| `festfinder-backend/src/services/ingest/` | Event intelligence: `adapters/` (website JSON-LD, ICS, Ticketmaster), `normalize.ts`, `resolve.ts` (deterministic dedupe), `confidence.ts` (rules + freshness), `run.ts` (the pipeline), `fetch.ts` (robots.txt, per-host spacing). Imports never publish: they merge into an event or wait in the review queue. |
| `festfinder-backend/src/lib/` | `i18n.ts` (`L(en, vi)`, genres), `places.ts` (countries and cities with timezone, currency, bounds; synced to the tables after every migration), `styles.ts` (music styles, event types, classifier), `money.ts`, `errors.ts`, `validate.ts` (`parse`, `limit`, `csv`), `time.ts` (`atZone`, `dateIn`, `isoIn` for event times; the `vn*` helpers for back-office dates), `format.ts`. |
| `festfinder-backend/src/db/migrations/` | Numbered SQL files, applied on boot. The next one is `045_*.sql`. Never edit a migration that has shipped. |
| `festfinder-backend/test/` | `node --test` on PGlite in memory. `helpers.ts` has `setup()`, `people.ts` has `emailUser()`, and `fixtures/seed.ts` is the demo data. Demo data exists only in the tests. |
| `festfinder-backend/e2e/` | Playwright. `next/` holds the checks of the site, the Console, Studio and the artist studio; `playwright.next.config.ts` runs them against a production Next build with the API behind it. |
| `festfinder-frontend/ui/` | The files the site loads from `/ui`: `map/ff-map.js` (the map, loaded by `FF.loadMap()` in `festfinder-web/src/runtime/ff.ts`), `assets/` (brand images, favicons) and `vendor/` (MapLibre + pmtiles). The Next build copies `vendor`, `assets` and `map` to `festfinder-web/public/ui/`. |
| `festfinder-web/` | The Kính đêm ("night glass") redesign on Next.js 16: hand-written React 19 + Tailwind v4. Routes in `src/app/(kd)/`; the screens in `src/kd/` (`ui/` the parts, `web/`, `app/`, `studio/` (organisers), `artist/` (the artist studio, `/studio/artist`), `console/` (the team's back office; `console/kit.tsx` holds its shared parts), `feedback/` (the feedback sheet, opened by "Góp ý"), strings in `copy/` and each screen's `copy.ts`); `src/kd/theme.css` holds the tokens; `/kit` (with `FF_KIT=1`) shows every part. `src/runtime/ff.ts` is the browser runtime (`FF`). `scripts/copy-ui.ts` (`npm run copy-ui`) copies `public/ui/` from `festfinder-frontend/ui` before dev and build. Production runs this front at feestfinder.com; every path that is not one of its pages goes to the API through `src/proxy.ts`. |
| `docs/` | `CURRENT_ARCHITECTURE.md`, `TECH_DEBT.md`, `FEESTFINDER_IMPLEMENTATION_PLAN.md` (the event-intelligence plan and the decisions behind it) and `FEESTFINDER_ROADMAP.md`. Update the roadmap with the work. |

## Commands

Run from `festfinder-backend/` unless noted.

```bash
npm run typecheck          # tsc for src+test and for e2e; noUnusedLocals/Parameters are on
npm test                   # every API test (a few minutes)
node --test test/auth.test.ts                  # one file
npm run test:screens       # Playwright: e2e/next against a production Next build (3100) and its own API (4100, own PGlite)
npm run dev                # the API on :4000 against the staging database in .env
```

For the Next front, run `npm run dev` / `npm run build` from `festfinder-web/`. Both copy `public/ui/` first. `npm run lint` there runs type-aware ESLint: no errors, and no more warnings than the budget in its `package.json` (lower it when you fix some). In `festfinder-backend/`, `npm run lint` runs oxlint type-aware (through typescript-go, so it reads TypeScript 7), configured in `.oxlintrc.json`: no errors, and no more warnings than its `--max-warnings` budget (lower it when you fix some); `npm run lint:warnings` lists them.

## Rules this codebase follows

- **Copy:** server text uses `L('English', 'Tiếng Việt')`. Screen text on the site is `{en, vi}` pairs in `festfinder-web/src/kd/copy/` and each screen's `copy.ts`, read with `pick()`. The web defaults to Vietnamese.
- **Lean UI:** the user wants titles and actions, not explanations. Add a hint only for a format rule. No tips cards, no "why we ask" lines. No status line that counts the results or says when a list was updated.
- **Look:** the site (Kính đêm v2, design phase 0 on 2026-10-17): `surface-0` `#08090a`. Colour tokens are named for their role in `festfinder-web/src/kd/theme.css`, the only file that writes a hex colour: `surface-0/1/2`, `line-1/2`, `fg-1/2/3`, `inverse` / `on-inverse`, `info`, `lime`, `on-accent`, `ok` / `warn` / `bad`, `map`. Colour says one sentence: turquoise `info` `#00D9D0` is information (style names, links, the chosen tab, row or pin, counts, "free"); the turquoise → lime gradient (`--gradient-accent`: `#00D9D0` · `#72E679` · `#E4F222`) is the one action a screen exists for (`buttonClass({ tone: 'acc' })`, with `glow` on the one that leads the page), the "featured" tag (`kd-tag-featured`) and the logo's flags; lime alone is the focus ring and the glow; status is a dot with a word. Four button tones (`acc`, `default` outlined, `ghost`, `danger`); radii 4 / 8 / 16 and the pill; glass only over a photo or a map. `npm run lint` in `festfinder-web` runs `scripts/check-tokens.ts`: no hex colour outside `theme.css` (a literal that must stay says `tokens-ok`), no old token name (`scripts/tokens-v2.ts` renames them, `npm run tokens:rename`), and no more arbitrary `[Npx]` values than its budget, which only goes down. One type family, Noto Sans, for words and numbers alike (self-hosted from `@fontsource-variable/*`, declared in `kd/fonts.css`, which `festfinder-web/scripts/fonts-css.ts` writes on `npm run copy-ui`: a Vietnamese page fetches only the latin and vietnamese files; Thai text the Thai file; Noto Sans JP's stylesheet goes to `public/fonts/` and `kd/ui/script-fonts.tsx` adds it only on a page with CJK text; no Google Fonts request, and the CSP allows none; no monospace face: numbers line up with `kd-num`), icons from `@phosphor-icons/react` (Regular, imported per icon). Pages are full width on desktop: `.kd-wrap` has no max width, only the gutter (`--kd-gutter`: 16, 32, then up to 64px); long text keeps `max-w-read`, and card grids add columns rather than widen. The app's screens (`/app/…`: tickets, checkout, notifications, settings, alerts, the group plan, the guide, live mode, recap) wear the site's frame (`kd/app/root.tsx`, design v2 phase 4): its nav on top and, on a phone, its tab bar, which a screen's dock sits on; buying from the list never changes frame. A back button in the app or the Studio wizard goes back where the person came from on this site (`BackLink` / `goBack` in `kd/ui/back-link.tsx`), its fixed page only when they arrived from elsewhere. The site's frame (design v2 phase 1, `kd/web/chrome.tsx`): on a computer one bar with the logo, four places (Sự kiện, Nghệ sĩ, Dự án, Nhà tổ chức), the search field (⌘K or Ctrl+K; an icon from 900 to 1200px), VI · EN, "Đăng sự kiện" and the account menu; on a phone the logo and "Đăng sự kiện" on top and a tab bar at the bottom of every public page (Sự kiện, Bản đồ, Tìm, Đã lưu, Tôi; `TabBar` with `edge`), with the other places and the styles in the "Tìm" sheet. Styles are filters of the list, never a nav item. "Đăng sự kiện" goes straight to Studio's wizard (`/studio/new`); a project starts from `/p` (owner, 2026-10-17). "Tôi" is one list (`kd/web/me.tsx`): the account menu on a computer and the hub on `/profile` on a phone. The workspaces (attending, the craft, the Console for the team) are one list too (`kd/ui/workspaces.tsx`), in the account menu, the hub and the switcher at the head of every back office's rail; admins reach the Console there (`isTeam` in `kd/craft.ts`), not from the bar. Every logo is `Logo` (`kd/ui/logo.tsx`, logo pack v2: the compact wordmark, or the flag pole), a link home. No button floats over a page: "Góp ý" is in the footer, the account menu, the hub and the rails (they send `ff:feedback`). A detail page's breadcrumbs (`Crumbs`) show its list and itself, never the home crumb or EDM. Every genre family wears the information colour (`familyOf` / `g()` in `festfinder-web/src/kd/genre.ts` stay); a page without a cover shares logo pack v2's picture (`/ui/assets/og.png`, `ogFallback` in `services/seo.ts`), and the share-story art is the night ground with the accent's glow (`runtime/ff.ts`); chips name styles (`styleChips`, `styleLabel`). An event without a cover is a text tile, never shapes: `Art` in `kd/ui/parts.tsx` takes the `title` (with a turquoise `kicker`, the style, and a `meta` line) and shows the name set large, or a two-letter monogram under 160px wide; CSS draws those words from data attributes, so a card's name is never page text twice; `layout` is `card`, `banner` (a profile's cover) or `hero` (the event page). The back offices (`/console`, `/studio`, `/studio/artist`) are Kính đêm too: a side rail (`kd/ui/rail.tsx`, folded into a menu bar under 900px), tables of grid rows (`Table` / `Row` in `kd/ui/shell.tsx`: columns shrink, never hold a minimum width, and rows turn into cards in a container under 640px, or wider with `fold` `md` / `lg` / `xl` for a table of many columns), drawers from the right. Every screen fits the width of the device and nothing scrolls sideways, anywhere (the owner's rule): no `min-w-[…]` wrapper, no `overflow-x-auto` box; a row of tabs (`.kd-tabs`) or chips (`.kd-hscroll`) wraps to a second line. `e2e/next/layout.spec.ts` checks every role's screens at 390, 768 and 1440px, and `e2e/next/wcag.spec.ts` runs axe on the same screens at 390 and 1440px (no serious or critical WCAG 2.1 AA violation): an accessible name starts with the visible words, tabs that are links are a `nav` and tabs that switch in place a `tablist` with arrow keys (`Tabs` in `kd/ui/shell.tsx`), a sheet gives focus back to what opened it, and every page starts with a skip link to its `<main>` (`kd/ui/skip-link.tsx`, in the root layout). No browser scrollbar takes room: `kd.css` hides them all and `kd/ui/scrollbars.tsx` (in the root layout) draws a 3px thumb over whatever scrolls, only while it scrolls; don't style scrollbars per screen.
- **Changing a screen:** every screen is in `festfinder-web/src/kd/`. `/ops` is gone: the API redirects its old addresses (`opsPath` in `routes/frontend.ts`). The home page is the list of every event (`/`, `kd/web/list`; owner 2026-10-17): there is no "Khám phá" page on the web or in the app, and `/list` and `/map` redirect to `/` with their query (next.config.ts). The app's discovery went into the site (owner, 2026-10-17): `/app`, `/app/list`, `/app/saved`, `/app/profile` and `/app/e/<slug>` redirect for good to `/`, `/?view=map`, `/saved`, `/profile` and `/e/<slug>` with every query (`kd/app/moved.ts`); notification links name the site's pages. The installed app opens on `/?source=app` (the web manifest), which asks a device seen for the first time, nobody signed in, its city and styles in a two-step sheet (`web/list/first-run.tsx`) and then opens the list on that city; the site in a browser asks nothing. The event page carries the group plan and the guide rows the app's event screen had. The home page lists by day by default (`kd/web/list/days.tsx`: each of the first seven days a lead card with the next nights as rows beside it, then a heading per month; every event a row in a box under 600px), the table is `?view=table`, and from 1200px a rail holds the week ahead and the cities; its filters are one sticky bar (`.kd-cmd`; on a phone "Lọc" opens them all in a sheet); its questions live on `/about` with their FAQPage JSON-LD (owner, 2026-10-17). The event page has no bar of section tabs: its hero has the four facts (Thời gian, Địa điểm, Giá, Độ tuổi) and a 16:9 cover; on a phone the tickets come right after it and "Mua vé" stays within reach in a bar above the tab bar (`web/event/dock.tsx`, which steps aside while the ticket panel is on screen); the organiser's answers and everyone's posts are one "Hỏi đáp" (`web/event/community.tsx`), its rules behind a "Quy tắc" link, never a line telling people off.
- **The runtime:** there is one, `festfinder-web/src/runtime/ff.ts` (`FF`, with `src/kd/runtime.tsx`). The map stays in `festfinder-frontend/ui/map/ff-map.js`, which the Next build copies and `FF.loadMap()` loads.
- **Validation:** validate input with zod through `parse()`. Throw `AppError` helpers so the error reaches the client as `{error: {code, message}}`. Build SQL only with positional parameters (`$1` or `SqlParams.p()`). Interpolate column names only from fixed lists. A NUL character anywhere in a request (address, query, body) is refused as `invalid_input` before any handler (`app.ts`); Postgres would fail on it.
- **Sign-in:** Google first. OAuth comes back through `/auth/oauth/:provider/return`, which redirects with `?auth=…&via=…` or `?auth_error=…`. `GET /auth/providers` says which ways in are configured, and the sign-in card shows only those. `GET /auth/session?optional=1` answers `{user: null}` instead of a 401.
- **Personas and admin:** every account attends (a fan); besides that it has at most one craft, artist or organiser (`user_roles`, migration 033: the API refuses a second with `one_craft`, `POST /me/roles/switch` swaps them and keeps both profiles; the screens switch from the account menu and the workspace rails, `kd/craft.ts`). Listed profiles are claimed, never duplicated. Admin comes only from the `ADMIN_EMAIL` allowlist on a Google sign-in with a verified email: never add a route, role choice or shared password that grants it, and never write the allowlist into the repo. Every listing someone sends in (Studio, the community form, a change to a live listing) waits in the Console's review queue and every admin is told in the app, by push and by email (`askForReview`, `notifyAdmins`); what an admin posts goes live at once (`teamSession`). A change to a live listing keeps it on sale while it waits (`needs_review_*`, migration 040): approving clears the flag, rejecting puts the old values back.
- **Projects:** anyone signed in (no craft needed) pitches an idea for a night at `/p` (`routes/projects.ts`, `services/projects.ts`, migration 034): what it is, its budget, what it looks for (investment, sponsors, artists, a venue, a partner) and sponsor packages. The team reviews it before it is public (`/console/projects`); publishing needs a confirmed phone, like every post. Others offer (`invest`, `sponsor`, `perform` from an active artist profile, `venue`, `partner`); an accepted offer shows both sides each other's contact. FeestFinder never takes, holds or moves money, and every project page says so; never add a payment to it. A project linked to its event puts the accepted sponsors on the event page and in its JSON-LD (`Event.sponsor`).
- **Artists and gigs:** follower counts never rank an artist, a directory or a gig applicant. Network lines are read from events with their evidence, not stored. An artist's gig report is a source, never a publisher. The artist directory lives at `/a` (`/a/style/<style>`, `/a/city/<city>`) because `/artists` is the API. It lists only profiles an artist runs (made or claimed) or the team verified (`artistKind` 'owned', `services/artists.ts`; the owner confirmed on 2026-10-17 that a verified profile counts as owned); every other name events show, from a lineup or Radar, waits at `/a/radar` (`?kind=unclaimed`) with "Đây là tôi". The directory says which with tabs and their counts (Có hồ sơ · Từ Radar · Nhận booking: `/a`, `/a/radar`, `/a?booking=1`), never with a line explaining it; its cards are square (the photo, else the initials large: `Art` layout `mono`) with the next show, two to a row on a phone. An artist's page has no banner repeating the name: their cover only when they have one, then tabs (Sắp diễn · Mix · Đã diễn · Giới thiệu; `EventTabs` opens `#<key>` and `?mix=`), the latest mix beside them. "Đây là tôi" and "Tôi là nghệ sĩ" send `role_picker_shown` (role, surface), so claims can be counted. A follow is of a profile (`artist_follows.artist_id`, migration 041), never of an unclaimed name ("Nhắc khi có show" adds it to Smart Alerts instead), and nobody follows their own page; when an artist takes a profile over, follows and alerts of the name move to it. A profile an artist runs is the official one for its name, and lineups meet it by handshake (`services/lineup.ts`, `event_artists.confirmed_*`): an organiser who lists the artist asks them in the app to confirm ("Đây là tôi" / "Không phải tôi", a dispute unlinks the name for that event), an artist's gig report on a listed night asks the organiser to add them, and the profile shows only confirmed shows. Followers and following are read from real follows only (`services/follows.ts`, migration 042): people follow artist profiles, organisers and people (`user_follows`, `PUT /me/follows/people/:id`); a profile's following is what the accounts that run it follow; nobody follows their own page or themselves; `organizers.followers_count` is kept equal to its follows by a trigger and never seeded. A person manages both lists on their profile (`kd/ui/follows.tsx`).
- **Analytics:** `FF.track(name, props)` only with a name in `CLIENT_EVENTS` and keys in `ALLOWED_PROPS` (`services/analytics.ts`); never an email, a name or an IP. Nothing leaves without `POSTHOG_KEY`.
- **Production data:** there is no demo data and no seed in production, and there must never be a fallback database. Production and staging Supabase projects refuse each other's labels.
- **Places, time and money:** never hard-code a city, a UTC offset or `₫`. A city comes from `lib/places.ts` (add one there; it is synced to the `cities` table); an event's instants use its city's timezone (`atZone`, `isoIn`); prices are whole units of `events.currency`, shown with `formatMoney` / `money()` (`festfinder-web/src/kd/format.ts`). FeestFinder checkout and ticket tiers are VND only. FeestFinder charges buyers no fee, on tickets or on resale: what a buyer pays is the price less any discount.
- **EDM only:** the one genre is `EDM` (`lib/i18n.ts` `GENRES`, a database check since migration 031); people filter by its styles (`lib/styles.ts` `STYLES`, `?style=`). An import that names another genre and no EDM style is dropped (`OTHER_GENRES`), one with no style waits for review, and approving it makes it EDM. Sources that list every kind of music set `requireStyle`.
- **Posted or Radar:** every event and artist is one or the other, and the site says which. `events.origin` is `radar` when nobody on FeestFinder posted it (no `organizer`, `community`, `team` or `artist` source), only Feest Radar (ingestion) found it; `refreshConfidence` keeps it current, so an organiser claiming it makes it posted. An artist is Radar when nobody runs or verified the profile and every event it plays is Radar (`ORIGIN` in `services/artists.ts`). `?origin=posted|radar` filters `/events`, `/events/map` and `/artists`; `facets.origin` / `origins` count them. On the site, `kd/ui/origin.tsx`: `RadarTag` on anything Radar found, the "Nguồn" filter (Mọi nguồn · Đã đăng · Radar) on the home page's list (`/`), and the artist directory's tabs (Có hồ sơ · Từ Radar · Nhận booking), and a Radar event's page names Feest Radar instead of its placeholder organiser. The local preview seeds a few Radar finds (`SEED_RADAR=1`, `test/fixtures/radar.ts`); the screen tests do not.
- **Sources:** ingestion is one more source next to organisers and the community, never a publisher. No adapter for Resident Advisor or Facebook (their terms forbid it); their links are kept as provenance only. New adapters go in `services/ingest/adapters/` and `ADAPTERS`, with fixture tests in `test/ingest.test.ts` (no live requests).
- **Feest Radar:** two placeholder organisers hold events nobody runs yet (`services/community.ts` `PLACEHOLDER_ORGS`, `organizers.placeholder`, migration 044): Feest Radar (`/o/feest-radar`) holds what ingestion finds, Cộng đồng FeestFinder (`/o/cong-dong`) what people send in (the community form, an artist's gig report). Both are `is_community` (claimable, nobody to warn or tell), and each is made with its first event, never on an empty database. Styles follow Beatport's dance genres (`lib/styles.ts`, mirrored in `festfinder-web/src/kd/genre.ts`, a test checks both), and a lineup of known artists (`lib/known-artists.ts`, whole names only) gives a night its style when the source names none. Every candidate gets a fit score for the team (`services/ingest/fit.ts`: the project's criteria and its people's, with reasons; Console queue sorts and filters by it); a new find under `FIT_FLOOR` is dropped as `low_fit`, unless it is a festival Radar watches (`lib/festivals.ts`: `world` brands such as Tomorrowland, Ultra, EDC, Defqon.1 and Verknipt are kept in any known Asian city, launched or not, listed anywhere, highlighted on cards and on the home page, and first in the queue; `asia` brands only weigh in). A Radar find (origin radar) is marked `expired` a day after `ends_at`, the end of its last day (`services/ingest/expire.ts`, hourly job); nothing is deleted and an admin can restore it.
- **Images:** only an event's own media is uploaded (`POST /uploads?purpose=cover|logo|recap`: its cover and logo, and the photos fans take at it). Every other picture (a person's photo, an artist's photo and cover, an organiser's logo and cover, a project's cover, moments) is an https link checked by `probeImage` / `imageChange` (`services/remote-images.ts`) when it changes, and weekly by the `checkRemoteImages` job; the screens use `kd/ui/image-link.tsx`. Never add an upload purpose for a profile. Linked images load with `referrerPolicy="no-referrer"`, and a broken one leaves the initials or the art (`kd/ui/covers.tsx`). A picture's framing (the point to keep in view and a zoom) travels in its link as `#ff=x,y,z` (`lib/frame.ts`, `kd/frame.ts`): `Art`, `Avatar` and `FramedThumb` draw it, the editor is `FrameButton` (`kd/ui/frame-editor.tsx`, on every image field), the API checks, compares and notifies by the link without it (a new framing of the same picture is not checked again or sent to review), and SEO drops it.
- **Mixes:** an artist's SoundCloud, Mixcloud and Spotify sets (`lib/mixes.ts`, `routes/mixes.ts`). Never store or render a service's oEmbed HTML: `embedFrom` rebuilds the player's address on the hosts in `EMBED_HOSTS`, which must match `frame-src` in `festfinder-web/next.config.ts`. Nothing from a service loads before play. Likes and comments never rank anyone; commenting needs a confirmed phone.
- **Rides:** "Đặt xe" opens Grab, Be or Green SM by the country of the event's city (`lib/rides.ts`), never a hard-coded city. No app fills the destination until a partner link says how; the address is copied instead. The phone remembers the app chosen (`ff:ride-app`, browser only): the next tap opens it at once with "Đổi app" in the toast, and a city with one app opens it at once; an app with a universal link (Be's OneLink) opens through it on an iPhone (`web/event/ride.tsx`).
- **Event actions:** "Chỉ đường" opens Google Maps' route to the venue at once (`web/event/directions.ts`), never an anchor on the page. "Thêm lịch" opens the person's own Google Calendar with the night filled in (`authuser` is their email; Android opens the calendar app with an INSERT intent), and the `.ics` stays in its menu for Apple and Outlook (`web/event/calendar.tsx`).
- **Feedback:** the widget (`kd/feedback/`, in the root layout) sends `POST /feedback` (`routes/feedback.ts`); the server stamps the ticket and who sent it, and keeps the page's telemetry to its fixed list (paths without their query). Screenshots are served to the team only and deleted after 90 days; a GitHub issue never names who sent the report.
- **Advertising:** posting an event is free and goes through review. Promoting one is a request from Studio (`/studio/ads`, `routes/organizer/ads.ts`: the event, placements from `EVENT_AD_PLACEMENTS`, a budget, dates within the event, a note); brands book from `/advertise` with their details (`POST /ad-inquiries`: logo, website and social pages, product images as links, category from `AD_CATEGORIES`, contact, budget, dates, placements, cities). Every admin is told; the team answers both in `/console/featured` with a reply, and an approved request becomes an `ad_campaigns` row that only runs inside its dates. Ads are sold in VND (`lib/ads.ts`).
- **Ticket buttons:** every one goes through `/go/<event>` (`routes/outbound.ts`), never straight to `ticket_url`: it counts the click, picks FeestFinder's checkout or the seller, and adds a partner's tracking (`services/partners.ts`, `/console/partners`).
- **Map:** the map view asks `/events/map` when it opens and on "search this area" only, never on pan. The basemap is two self-hosted PMTiles archives, cut by `festfinder-backend/scripts/build-tiles.sh`: `MAP_OVERVIEW_URL` (the whole world, zoom 0–6, drawn below zoom 7) and `MAP_TILES_URL` (the listed cities, zoom 0–14, drawn from zoom 7, so no tile is drawn twice), on Vercel Blob (store `feestfinder-tiles`, `tiles/<planet build>/…`). Street, ward and city names use the site's own Noto Sans glyphs in `festfinder-frontend/ui/map/glyphs` (`MAP_GLYPHS_URL` overrides them). Without the archives the map draws the board and the events. Rebuild the tiles after adding a city, upload them under a new build folder and point the variables there.
- **Commits:** commit, push or deploy only when the user asks. A push to `main` is a production deploy.

## Skills and MCP (for coding agents)

## Caching (frontend.ts)

Outside development, the `/ui` URLs in CSS carry `?v=<content hash>`:
- `stampUrls()` adds it.
- Versioned files are `immutable`; the same file without it gets `max-age=3600`.
- Vercel starts a fresh CDN cache on every deployment.
- Responses for a signed-in person get `private, no-store` (`app.ts` onSend hook).
- Public reads without a session (`PUBLIC_READS` in `app.ts`) get `Vercel-CDN-Cache-Control: max-age=60, stale-while-revalidate=60` (only Vercel's CDN keeps them; the browser's `Cache-Control` stays `max-age=0, must-revalidate`, so it never shows a stale anonymous copy after sign-in) and vary on `X-FF-Session`, which the web proxy sets to 1 for a visitor with a session cookie and the web app's server renders (`lib/api.ts`) set to `render`; a request with it is never given or stored a shared copy. After a save, the screen calls `freshen` (`festfinder-web/src/kd/fresh.ts`, which posts to the route handler `app/kd-fresh/route.ts`; not a server function, which would refresh the router and drop filters kept in the address) so the public pages it changed render again at once. Never vary on `Cookie`: Vercel's CDN does not cache such a response.

## Deploying

- Two Vercel projects, both in `hnd1` (Tokyo), next to the Supabase database:
  - `feestfinder-web` (root directory `festfinder-web`) holds feestfinder.com (`www` and `feestfinder.vercel.app` redirect to it). Its proxy (`src/proxy.ts`) forwards every non-page path to the API with fetch, signed with `WEB_PROXY_SECRET` so the API sees each visitor (`festfinder-web/README.md`, "Deploy on Vercel").
  - `feestfinder` (root directory `festfinder-backend`) is the API, at `https://feestfinder-api.vercel.app` (the web project's `FF_API_ORIGIN`). Its `PUBLIC_BASE_URL` and `CORS_ORIGINS` stay `https://feestfinder.com`.
- Pushing to `main` deploys production on both projects (both are linked to GitHub with `main` as the production branch). The API's other branches get preview deployments on the staging database; the web project builds `main` only (`festfinder-web/vercel.json`). Migrations run on boot.
- Work happens on a branch and reaches `main` by merge. CI (`.github/workflows/ci.yml`) runs on pushes to `main` and on pull requests.
- To ship the API from a branch without merging it, run `vercel deploy --prod --yes` from the repo root (the root `.vercelignore` leaves `festfinder-web` out).
- pg_cron calls `POST https://feestfinder.com/internal/jobs` every minute; the web proxy forwards it with its `Authorization`.
- There is no way back to the API's old screens: they were removed on 2026-10-09. To undo a bad web release, promote an earlier `feestfinder-web` deployment in Vercel (Instant Rollback).
- Secrets, such as `GOOGLE_CLIENT_SECRET`, are entered by the user in Vercel.

## Checking a change

1. `npm run typecheck`, then the test file for the area, then `npm test`; `npm run lint` in each package you changed.
2. Browser checks: `npm run test:screens` (the checks are in `e2e/next/`).
3. Add a test next to similar ones: API behaviour in `test/*.test.ts`, a page of the site or a back-office flow in `e2e/next/<area>.spec.ts`.
